# Архитектура

## Общая схема

```
Telegram (long polling)
        │
        ▼
   Dispatcher (aiogram 3)
        │
   middlewares:  DbSessionMiddleware → UserMiddleware
        │
        ▼
     handlers/          ← только диалог: что спросить, что показать
        │
        ▼
     services/          ← бизнес-правила и расчёты
        │
        ▼
 database/repositories/ ← запросы к SQLite через SQLAlchemy
```

Правило: хендлер не собирает SQL и не собирает HTML. Он вызывает сервис и
берёт готовый текст из `texts/ru.py`.

## Слои

| Слой | Пакет | За что отвечает |
|------|-------|-----------------|
| Конфигурация | `src/config.py` | `.env` через pydantic-settings, бизнес-параметры из `settings.ini` |
| Модели | `src/database/models.py` | ORM-модели, enum-статусы |
| Репозитории | `src/database/repositories/` | все запросы к БД |
| Сервисы | `src/services/` | расчёты, правила доступности, работа с Telegram API |
| Хендлеры | `src/handlers/` | сценарии диалога, FSM |
| Клавиатуры | `src/keyboards/` | inline-кнопки и CallbackData-фабрики |
| Тексты | `src/texts/` | все пользовательские строки и сборка сообщений |
| Утилиты | `src/utils/` | разбор ввода, форматирование |

## Ключевые решения

**Деньги — только `Decimal`.** В базе `unit_price` хранится строкой
(`Money(TypeDecorator)` над `String`), чтобы SQLite не превращал сумму во float.
Все расчёты — в `services/calculations.py`, он не знает ни про базу, ни про Telegram,
и поэтому полностью покрыт юнит-тестами.

**Время — только UTC.** `TZDateTime(TypeDecorator)` кладёт в SQLite naive-UTC и
возвращает aware-datetime. Пользователю время показывается в `TIMEZONE` из `.env`.

**Публичный идентификатор закупки — `public_token`,** а не автоинкрементный `id`.
Токен генерируется через `secrets.token_urlsafe` и используется в deep link.
`id` показывается людям как «номер закупки», но подобрать по нему чужую ссылку нельзя.

**Организатор не заводится как `Participant`.** Его количество лежит в
`Purchase.organizer_quantity` и участвует во всех расчётах. Так проще: не нужно
поддерживать «полуучастника» с особыми правами.

**Отказ участника — мягкий.** Строка `Participant` остаётся со статусом `CANCELLED`,
поэтому unique-constraint `(purchase_id, user_id)` не мешает повторному
присоединению — та же строка возвращается в `ACTIVE`.

**Сессия БД — одна на апдейт.** `DbSessionMiddleware` открывает её, коммитит при
успехе и откатывает при исключении. Хендлеры, которым нужно отправить уведомление
уже после сохранения, коммитят явно.

**Ленивая загрузка запрещена там, где она опасна.** `Participant.purchase`
объявлен как `lazy="raise"`: в async-контексте неявный lazy-load падает с
`MissingGreenlet`. Закупка всегда достаётся явным запросом, а связи
`Purchase.participants` и `Participant.user` грузятся через `selectin`.

**FSM — только на время диалога.** Хранилище в памяти (`MemoryStorage`).
После каждого завершённого шага важное уходит в базу; недописанный черновик
после рестарта теряется — это осознанный компромисс MVP.

## Проверки безопасности

- права проверяются заново по базе после каждого нажатия кнопки;
- `callback_data` содержит только идентификатор действия и объекта;
- пользователь идентифицируется по `telegram_id`, никогда по `username`;
- все пользовательские строки проходят `html.escape` перед вставкой в сообщение;
- Telegram ID участников видны только организатору и администратору, в группу не уходят;
- SQL пишется только через SQLAlchemy, конкатенации запросов нет;
- `BOT_TOKEN` не логируется нигде.

## Фоновые задачи

`services/deadline_checker.py` — один asyncio-таск внутри процесса бота.
Раз в `DEADLINE_CHECK_INTERVAL_SECONDS` находит `OPEN`-закупки с истёкшим
дедлайном, закрывает их, обновляет объявление и рассылает уведомления.
Первый проход выполняется на старте — так закрываются закупки, «просроченные»
во время простоя.

## Схема данных

```
users 1───* purchases (organizer_id)
users 1───* participants
purchases 1───* participants   (unique: purchase_id + user_id)
users 1───* rules_acceptances  (purchase_id nullable)
```

Статусы `Purchase`: `DRAFT → OPEN → CLOSED → ORDERED → SHIPPED → RECEIVED → COMPLETED`,
плюс `CANCELLED` из любого нефинального. В UI MVP используются `OPEN`, `CLOSED`,
`CANCELLED`; остальные заведены под будущие этапы (оформление заказа, доставка).
